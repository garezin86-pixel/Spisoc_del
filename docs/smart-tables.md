# Smart Tables

Таблицы в стиле Excel как **живое окно в базу CRM**: данные не копируются, правка (этап 4) идёт через
существующие сервисы, поэтому права, проверки и аудит те же, что в карточках.

## API (этап 1, только чтение)

- `GET /api/tables` — источники: `clients`, `deals`, `deal_items` («Оборудование») и самостоятельные таблицы `uct_<id>`, которые видит пользователь.
- `GET /api/tables/{source}/meta` — колонки: тип, операции фильтра, списки значений, флаги `editable`, `manager_only`, `linked`.
- `GET /api/tables/{source}/rows` — строки. Параметры: `columns` (через запятую), `filters` (JSON), `sort` (JSON), `page`, `size` (до 200).

Пример: выигранные сделки по менеджерам, крупные сверху:

```
GET /api/tables/deals/rows
  ?columns=owner_name,client_name,title,amount,currency
  &filters=[{"field":"stage_kind","op":"eq","value":"won"}]
  &sort=[{"field":"amount","direction":"desc"}]
```

В каждой строке есть служебные `_id` и `_version` (updated_at записи — токен для правки на этапе 4).
Деньги отдаются числом, как во всём API (`Money` в `schemas/deal.py`).

## Правила

- Колонки, фильтры и сортировка берутся **только из реестра** `src/services/table_registry.py`. Неизвестное поле, операция не для типа или значение не того типа — 422.
- Запросы идут через ORM-атрибуты (работает `tenant_scope`), `workspace_id` дополнительно ставится явно. Удалённые записи и сделки удалённых клиентов не показываются.
- Читают все пользователи компании, как обычные списки. Запросы — GET, поэтому read-only токены (PAT) тоже работают.
- Новая колонка = одна строка `ColumnDef` в реестре. Новый источник (например, задачи) = колонки + функция соединений.
- Запись через таблицы (этап 4) не должна использовать массовый `UPDATE`: слушатели аудита и инвалидации дашборда его не видят. Только ORM-объекты через сервисы.

## Оборудование сделки (этап 2)

Одна строка — одно оборудование: **название** (свободный текст) и **цена** (вводится вручную, можно не указывать).
Справочника цен и количества нет. Валюта строки — валюта сделки. Цена позиции **не меняет** сумму сделки.

- `GET /api/deals/{id}/items` — строки сделки (читают все).
- `POST /api/deals/{id}/items` — добавить `{"name": "...", "price": 120.5}`.
- `PATCH /api/deals/{id}/items/{item_id}` — изменить; `price: null` очищает цену.
- `DELETE /api/deals/{id}/items/{item_id}` — мягкое удаление (история в аудите).
- `GET /api/deal-items/suggest?q=` — подсказка ранее введённых названий (частые сверху, регистр не плодит дубли).

Права: ответственный за сделку, admin, manager. **После закрытия сделки (Успех/Отказ) — только admin и manager.**
До 100 позиций в сделке. Название 1–200 символов, цена ≥ 0 с двумя знаками.

Таблица «Оборудование» (`source=deal_items`): строка — позиция; менеджер, клиент, стадия, дата закрытия берутся из сделки.
Отчёт «кто что кому продал»: `filters=[{"field":"stage_kind","op":"eq","value":"won"}]`,
колонки `owner_name,client_name,name,price,currency`.

## Свои поля (этап 3)

Колонки, которых нет в CRM («ЛС», «Тариф», «Результат»), у клиентов и сделок. Таблицы `clients` и `deals` не меняются.

- Типы: `text`, `number` (до 4 знаков после запятой), `date` («ГГГГ-ММ-ДД»), `select` (значения в `options`), `boolean`.
  Тип после создания не меняется. Название уникально в пределах сущности (без учёта регистра), до 30 полей на сущность.
- Хранение: **типизированные колонки** `value_text / value_number / value_date / value_bool` в `custom_field_values`
  (одна строка на пару «поле, запись»), а не JSON: фильтры и сортировка работают как у обычных колонок, без приведения
  типов и без различий между PostgreSQL и SQLite. Очистка значения обнуляет колонки, строка остаётся (изменения видны в аудите).

API:

- `GET /api/custom-fields?entity_type=client|deal` — поля (читают все).
- `POST /api/custom-fields` — создать `{"entity_type":"client","name":"ЛС","field_type":"text"}` (admin, manager).
- `PATCH /api/custom-fields/{id}` — название, `options` (только select), порядок (admin, manager).
- `DELETE /api/custom-fields/{id}` — мягкое удаление: колонка исчезает, значения остаются в базе (admin, manager).
- `GET /api/custom-fields/values?entity_type=&entity_id=` — заполненные значения записи.
- `PUT /api/custom-fields/{field_id}/values/{entity_id}` — задать значение; `null` или пустая строка очищает.
  Права как на правку самой записи: ответственный, admin, manager.

Колонки в таблицах (ключ `cf_<id>`, они же в `/meta`):

| Источник | Свои поля |
|---|---|
| `clients` | поля клиента (правка) |
| `deals` | поля сделки (правка) и поля клиента «Клиент: …» (только чтение) |
| `deal_items` | поля сделки «Сделка: …» и клиента «Клиент: …» (только чтение) |

Пример отчёта «кто что кому продал» с ЛС клиента: источник `deal_items`, колонки
`owner_name,client_name,cf_<ЛС клиента>,name,price`, фильтр `stage_kind = won`.

## Самостоятельные таблицы (этап 4, шаг 4.1)

Таблицы, которые пользователь создаёт сам: свои колонки и (с шага 4.2) строки, без привязки к CRM. Название семейства —
`user_custom_*`, чтобы не путать со «своими полями» клиентов и сделок (`custom_fields`, этап 3).

- Таблица принадлежит **компании** (`TenantMixin`); `owner_id` — отдельное поле с `ON DELETE SET NULL`.
  Если владелец уволен, данные остаются, admin или manager назначает нового.
- Видимость: `private` — владелец, admin, manager (для остальных таблицы «нет»: 404); `shared` — вся компания;
  `restricted` — они же плюс участники (шаг 4.5).
- Создать таблицу может любой пользователь; менять настройки, колонки и удалять — владелец, admin, manager;
  сменить владельца (`owner_id`) — только admin и manager.
- Типы колонок: `text`, `number`, `date`, `boolean`, `select` (значения в `options`) и связи `client`, `deal`, `user` (шаг 4.4). Тип после создания не меняется.
  Ключ колонки `c<id>` не меняется при переименовании. Название уникально в таблице (без учёта регистра).
- Лимиты: 100 таблиц на компанию, 50 колонок в таблице (константы в `user_custom_table_service.py` и
  `schemas/user_custom_table.py`). Удаление таблиц и колонок мягкое.

API (`/api/user-custom-tables`):

- `GET ""`, `POST ""` — список видимых таблиц; создать (можно сразу с `columns`).
- `GET /{id}`, `PATCH /{id}`, `DELETE /{id}` — таблица с колонками; изменить (название, описание, иконка, видимость, `owner_id`); удалить.
- `POST /{id}/columns`, `PATCH /{id}/columns/{column_id}`, `DELETE /{id}/columns/{column_id}` — колонки (название, `options`, `position`).

### Строки (шаг 4.2)

- Строки добавляет, правит и удаляет **каждый, кто видит таблицу**: в общей таблице вся компания (совместная работа),
  в личной — владелец, admin, manager. Структуру (колонки) по-прежнему меняют только владелец, admin, manager.
- Значения проверяются по типу колонки (`services/value_coercion.py` — те же правила, что у своих полей):
  text/select — строка (select — из списка), number — число до 4 знаков после запятой, date — «ГГГГ-ММ-ДД»,
  boolean — true/false (`false` — значение, а не очистка). `null` или пустая строка очищает ячейку.
- Хранение: строка `user_custom_table_rows` и ячейки `user_custom_table_cells` с типизированными `value_*`
  (как у своих полей). Пустая ячейка отдельной записью не создаётся. Удаление строк мягкое.
- **Версия строки** — её `updated_at`; меняется при записи любой ячейки (если значение реально изменилось).
  Правка с `version` от устаревшей версии — **409**; без `version` последняя запись побеждает.
- Лимит: 50 000 строк в таблице (`MAX_ROWS_PER_TABLE` в `user_custom_table_row_service.py`).

API:

- `GET /api/user-custom-tables/{id}/rows?page=&size=` — строки по порядку добавления (`values` — по ключам колонок `c<id>`).
- `POST /api/user-custom-tables/{id}/rows` — `{"values": {"c12": "Роутер", "c13": 15}}`.
- `PATCH /api/user-custom-tables/{id}/rows/{row_id}` — `{"values": {...}, "version": "<updated_at>"}`.
- `DELETE /api/user-custom-tables/{id}/rows/{row_id}`.

### Самостоятельные таблицы в общем движке (шаг 4.3)

Каждая самостоятельная таблица доступна как источник **`uct_<id>`** в тех же эндпоинтах `GET /api/tables/{source}/...`,
что клиенты и сделки: те же фильтры, сортировка, страницы, `columns`, `_id` и `_version`.

- Колонки источника: пользовательские колонки таблицы (ключ `c<id>`, подпись — название колонки; переименование
  меняет подпись, а не ключ) и служебные `id`, `created_by_name`, `created_at`, `updated_at`. По умолчанию
  возвращаются пользовательские колонки.
- Тип колонки определяет допустимые операции (как у остальных источников): text — `eq/ne/contains/in/is_null/not_null`,
  number и date — сравнения, select — только значения из списка, boolean — `eq`.
- Видимость: общая таблица — вся компания, личная — владелец, admin, manager; чужая личная и несуществующая —
  одинаково 404, в `GET /api/tables` такая таблица не показывается. Ключи `uct_abc`, `uct_0`, `uct_012` — 404.
- В выдаче нет удалённых строк, строк соседних таблиц и удалённых колонок; фильтровать по удалённой или чужой колонке нельзя (422).
- `_version` строки подходит как `version` при правке строки (`PATCH .../rows/{row_id}`): на нём строится защита от одновременной правки.

Пример: склад, где состояние «Новый» и осталось меньше 10 штук:

```
GET /api/tables/uct_7/rows
  ?filters=[{"field":"c31","op":"eq","value":"Новый"},{"field":"c28","op":"lt","value":10}]
  &sort=[{"field":"c28","direction":"asc"}]
```

Заметка по производительности: значение ячейки читается подзапросом по паре (строка, колонка). Для таблиц до
десятков тысяч строк это нормально; если сортировка по колонке станет медленной, добавим составной индекс по
`(column_id, value_*)` отдельной миграцией.

### Колонки-связи с CRM (шаг 4.4)

Типы колонок `client`, `deal`, `user`: ячейка хранит **id** клиента, сделки или пользователя (одна связь на ячейку).
Колонка необязательна, таблица без связей работает как раньше.

- При записи сервер проверяет, что запись существует в **этой же компании** и не удалена (клиент, сделка). Читать клиентов
  и сделки могут все пользователи компании, поэтому отдельной проверки доступа нет. Чужая, удалённая или несуществующая
  запись — 422: «Колонка «Клиент»: Клиент с id 99999 не найден». Значение — целое число или строка из цифр.
- Правка соседних ячеек не зависит от удалённой связи: связь перепроверяется только если значение действительно меняется.
- В таблицах (`uct_<id>`) каждая связь даёт две колонки, как «Клиент (id)» и «Клиент» в таблице сделок:
  `c<id>` — id (фильтры `eq/ne/in/is_null/not_null`, правка) и `c<id>_name` — название для показа и поиска
  (клиент — имя, сделка — название, пользователь — логин; текстовые фильтры и сортировка работают). По умолчанию
  возвращается `c<id>_name`. Через `PATCH` строки писать можно только в `c<id>`.
- **Целостность:** переименование записи сразу видно в таблице. Если связанная запись удалена, id остаётся, а название
  показывается как **«(удалён)»** — битой ссылки нет, такие строки легко найти фильтром `c<id>_name = (удалён)`.
  Нет связи — `null`.
- Во внешнем ключе нужды нет: ссылка идёт на разные таблицы, поэтому целостность обеспечивает сервис (`value_ref` в
  `user_custom_table_cells` и индекс по нему — пригодится для обратного списка «где использован этот клиент»).
- В `GET .../rows` (список строк самостоятельной таблицы) связь возвращается id; названия берите из `GET /api/tables/uct_<id>/rows`.

### Ограниченный доступ (шаг 4.5)

Видимость `restricted`: таблицу видят владелец, admin, manager и **участники** — выбранные пользователи компании.
Для остальных такая таблица неотличима от несуществующей (404) во всех эндпоинтах и в списке источников.

| Кто | Видит | Правит строки | Меняет структуру, настройки, участников |
|---|---|---|---|
| Владелец, admin, manager | да | да | да |
| Участник с `can_edit: true` | да | да | нет |
| Участник с `can_edit: false` | да | нет (**403**) | нет |
| Остальные | нет (404) | нет | нет |

- `GET /api/user-custom-tables/{id}/members` — участники (видят только владелец, admin, manager).
- `PUT /api/user-custom-tables/{id}/members` — `{"members": [{"user_id": 5, "can_edit": false}]}`: **заменяет список целиком**,
  кого нет в списке, теряет доступ сразу. До 100 участников, каждый — пользователь этой компании (иначе 422).
- Структуру и список участников участник менять не может: нельзя самому расширить себе или другим доступ.
- Список можно подготовить заранее: доступ участники получают только при видимости `restricted`. Если сменить
  видимость на `private` или `shared` и вернуть `restricted`, список участников сохраняется.
- Удаление участника мягкое, при повторном добавлении запись восстанавливается; создание, смена права, удаление и
  восстановление пишутся в аудит. Если владелец уволен, участники доступа не теряют, нового владельца назначает admin или manager.
- В `GET /api/user-custom-tables` и карточке таблицы есть флаги `can_edit_rows` и `can_manage` для текущего пользователя
  (интерфейс по ним скрывает кнопки). Сервер проверяет права сам независимо от флагов.
- Миграция только добавляет таблицу `user_custom_table_members`; значение `restricted` помещается в существующую колонку `visibility`.

### Импорт CSV и Excel (шаг 4.6)

Два сценария на базе тех же функций чтения файла, что у импорта клиентов (`client_import_service.read_table`:
кодировки cp1251/utf-8, разделитель «,» или «;», .xlsx, до 5 МБ и 5000 строк за раз). Дополнительно не больше
**30 000 ячеек** (строки × колонки) за один импорт: каждая ячейка пишется в аудит, замер — 25 000 ячеек за ~12 с.
Больше — частями.

1. **В существующую таблицу** — `POST /api/user-custom-tables/{id}/import/columns` и `POST /api/user-custom-tables/{id}/import`
   (multipart: `file`, `mapping`, `dry_run`).
   - `.../import/columns` отдаёт колонки файла с примерами и подсказанным типом, колонки таблицы (`importable: false`
     у связей) и `suggested_mapping` по совпадению названий без учёта регистра.
   - `mapping` — JSON `{"c12": 0, "c13": 2}`: ключ колонки таблицы → номер колонки файла (с 0). Колонки-связи
     (`client`, `deal`, `user`) из файла не заполняются (422).
   - Доступно тем, кто может менять строки таблицы (участник только для чтения — 403, чужая личная — 404).
2. **Создать таблицу из файла** — `POST /api/user-custom-tables/from-file/columns` и `POST /api/user-custom-tables/from-file`
   (multipart: `file`, `name`, `visibility`, `columns`, `dry_run`). Доступно любому пользователю компании, владелец — тот,
   кто импортирует. `columns` — необязательный JSON `[{"index": 0, "name": "Лицевой счёт", "data_type": "text"}]`:
   какие колонки файла брать и каким типом (`text`, `number`, `date`, `boolean`, `select` с `options`). Без него берутся все
   колонки (до 50) с подсказанными типами; одинаковые заголовки получают номера («Имя», «Имя (2)»), пустой — «Колонка N».

**Как приводятся значения** (неверное значение не отменяет импорт: ячейка остаётся пустой, в отчёте — предупреждение
с номером строки файла и названием колонки; строка без единого значения пропускается и попадает в `errors`):

| Тип | Что понимает |
|---|---|
| number | `12.5`, `12,5`, `1 234,50`, `1.234,50`, `1,234.50`; до 4 знаков (лишние округляются с предупреждением) |
| date | `ДД.ММ.ГГГГ`, `ГГГГ-ММ-ДД` и остальные форматы импорта клиентов, а также ячейки-даты Excel |
| boolean | да/нет, yes/no, true/false, +/−, 1/0, ячейки-флажки Excel |
| select | значение из списка без учёта регистра; другое — предупреждение, ячейка пуста |
| text | как есть; длиннее 2000 символов обрезается с предупреждением |

**Подсказка типа** (для создания из файла и `.../columns`): тип подходит, только если подходят **все** значения, иначе `text`
(без потерь). Числа с ведущим нулём (`0123456`) и длинные цифровые значения (9+ цифр: телефон, ЛС, ИНН) остаются
текстом, чтобы не потерять вид; `0/1` — число, а не да/нет. Тип всегда можно задать явно в `columns`.

`dry_run=true` ничего не пишет и возвращает тот же отчёт (`total_rows`, `to_create`, `errors`, `warnings`, `preview` —
первые 10 строк). Строки (и новая таблица) создаются **одной транзакцией**: либо всё, либо ничего. Лимиты проверяются
и в предпросмотре: в таблице не больше 50 000 строк, в компании не больше 100 таблиц. Номера строк в отчёте считаются без
учёта полностью пустых строк файла (как и в импорте клиентов).
