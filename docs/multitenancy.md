# Мультитенантность: решение и правила

## Решение

Один общий сервис для нескольких компаний. Компания — это `workspace`; данные компании
помечены `workspace_id`. Отдельный инстанс на каждого клиента **не** используется.

Решение принято на Этапе 0 и реализовано на Этапе 0.5. Изоляция данных — логическая, поэтому
она проверяется тестами с двумя компаниями (`tests/test_tenant_*.py`,
`tests/test_workspace_*.py`), а не принимается на веру.

## Как устроена изоляция

**Какие таблицы принадлежат компании.** Таблицы с `TenantMixin` (`src/models/mixins.py`):
`users`, `groups`, `spisok_del`, `comments`, `projects`, `tags`, `attachments`, `chat_messages`,
`task_checklist_items`, `task_dependencies`, `task_templates`, `webhooks`, `workspace_invites`.
`audit_log` не использует миксин: там `workspace_id` nullable и берётся с изменяемой сущности,
для него в фильтре чтения есть отдельное правило. Таблицы без `workspace_id`
(`notification_settings`, `personal_access_tokens`, `push_subscriptions`, `notification_logs`,
`filter_presets`, `two_factor_recovery_codes`, `task_template_items`) принадлежат пользователю
или родительской записи и читаются только по ним.

**Запись.** `workspace_id` проставляется автоматически перед сохранением (`before_flush`,
`src/db/tenant_scope.py`).

**Чтение.** К каждому ORM-запросу сессии, привязанной к компании, автоматически добавляется
`workspace_id = :ws` (`do_orm_execute` + `with_loader_criteria`): SELECT, JOIN, count,
UPDATE, DELETE, ленивые загрузки. Вручную фильтровать в сервисах не нужно.

**Привязка сессии к компании:**
- HTTP и PAT: `get_current_user` (`src/core/dependencies.py`);
- Telegram-бот: `WorkspaceContextMiddleware` на каждый апдейт (сообщения и кнопки) через
  `ContextVar`; кроме того, `UserRepository.get_by_telegram_id` привязывает сессию к компании
  найденного пользователя;
- фоновые задачи: `UnitOfWork(..., workspace_id=...)` или `uow.set_workspace(...)` после того,
  как объект загружен по id.

**Границы фильтра** (важно знать, прежде чем на него полагаться):
- Сессия без привязки к компании **не фильтруется** (fail-open). Так работают логин и
  регистрация, планировщик напоминаний, диспетчер вебхуков, SQLAdmin (платформа) и сам
  `get_current_user` в момент загрузки пользователя.
- Фильтр не действует на сырой `text()`, чистый Core без ORM-сущности и на `session.get()`
  объекта, уже лежащего в identity map этой сессии.

## Глобально уникальные значения

`users.login`, `users.telegram_id`, `users.calendar_feed_token` уникальны по всей системе.
`users.username` уникален только внутри компании (`UNIQUE(workspace_id, username)`).
Поиск по глобально уникальному полю в привязанной сессии выполняется с опцией
`SKIP_WORKSPACE_SCOPE` (см. `UserRepository.get_by_login`).

## Роли

- `role="admin"` — администратор **своей** компании (приглашения, пользователи компании).
- `is_platform_admin` — доступ в SQLAdmin ко всем компаниям. Выставляется только вручную в БД,
  никогда через API, регистрацию или приглашения.

## Регистрация и приглашения

- `POST /api/auth/register` принимает ровно одно из: `company_name` (новая компания, пользователь
  становится её `admin`) или `invite_token` (присоединение с ролью `user`).
- Создание компаний выключено по умолчанию: `ALLOW_COMPANY_REGISTRATION=true` включает его.
  Вход по приглашению от флага не зависит.
- Приглашение (`workspace_invites`) действует 7 дней, без лимита использований, до отзыва.
  Админ управляет ими через `/api/workspace/invites`.
- Присоединиться можно по веб-ссылке `/?invite=<код>` или в боте: `/start ws_<код>`.
  Старого ручного одобрения заявок больше нет.

## Отключённая компания

`workspaces.is_active = false` (включается в SQLAdmin, раздел «Компании»): вход и выданные токены
(JWT, refresh, PAT) перестают работать, бот не отвечает пользователям компании, WebSocket
не подключается, iCal-ссылка не отдаётся, напоминания и вебхуки компании не отправляются.
Данные не удаляются, компанию можно включить обратно.

## Мост общего чата с Telegram

Группа одна на сервис и привязана к одной компании: нужны оба параметра `CHAT_BRIDGE_GROUP_ID` и
`CHAT_BRIDGE_WORKSPACE_ID`. Без `CHAT_BRIDGE_WORKSPACE_ID` мост выключен.

## Правила для нового кода (CRM и дальше)

1. Таблица с данными компании получает `TenantMixin`. Если миксин невозможен (как у `audit_log`),
   правило добавляется в фильтр чтения в `src/db/tenant_scope.py` отдельно.
2. К новой таблице обязательно пишется тест с двумя компаниями: чтение, чтение по чужому id,
   изменение и удаление чужой записи.
3. Не использовать `text()` и чистый Core для данных компании: фильтр на них не действует.
4. Код, работающий без пользователя (фоновые задачи, бот вне апдейта), привязывает сессию к
   компании явно, после загрузки объекта по id.
5. Значение, которое должно быть уникальным глобально, ищется с `SKIP_WORKSPACE_SCOPE`; уникальное
   в пределах компании включает `workspace_id` в составной ключ.
